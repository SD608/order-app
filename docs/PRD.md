# 커피 주문 앱 PRD

## 1. 문서 개요

### 1.1 프로젝트명

커피 주문 앱

### 1.2 문서 목적

본 문서는 커피 주문 앱의 프런트엔드 `주문하기` 화면에 대한 제품 요구사항을 정의한다. 사용자가 메뉴를 확인하고 옵션을 선택한 뒤 장바구니에 담아 주문을 완료하는 전체 흐름과 화면 동작을 기준으로 한다.

### 1.3 프로젝트 목적

사용자가 별도의 로그인이나 결제 절차 없이 커피 메뉴를 빠르게 선택하고 주문할 수 있으며, 관리자는 접수된 주문을 확인하고 관리할 수 있는 간단한 풀스택 웹 앱을 제공한다.

### 1.4 개발 범위

- 주문하기 화면: 메뉴 조회, 옵션 선택, 장바구니 추가 및 주문
- 관리자 화면: 메뉴·재고 관리 및 주문 상태 관리
- 메뉴와 주문 데이터의 생성·조회·수정·삭제

본 문서는 위 범위 중 `주문하기` 화면을 우선 정의한다.

## 2. 기술 스택

- 프런트엔드: HTML, CSS, React, JavaScript
- 백엔드: Node.js, Express
- 데이터베이스: PostgreSQL

## 3. 주문하기 화면 개요

### 3.1 사용자

- 매장에서 커피를 주문하는 일반 사용자
- 비회원 사용자를 기본 대상으로 한다.

### 3.2 사용자 목표

1. 판매 중인 커피 메뉴와 가격을 확인한다.
2. 메뉴별 옵션을 선택한다.
3. 원하는 메뉴를 수량과 함께 장바구니에 담는다.
4. 주문 내역과 총 금액을 확인한다.
5. 주문하기 버튼을 통해 주문을 접수한다.

### 3.3 성공 지표

- 사용자가 메뉴 선택부터 주문 접수까지 막힘없이 완료할 수 있다.
- 장바구니의 메뉴, 옵션, 수량, 금액이 사용자의 선택과 일치한다.
- 주문 접수 시 중복 주문이나 잘못된 총 금액이 발생하지 않는다.

## 4. 화면 구성 및 레이아웃

와이어프레임 기준으로 화면은 상단 내비게이션, 메뉴 목록, 장바구니 영역으로 구성한다.

### 4.1 상단 헤더

- 브랜드명 `COZY`를 왼쪽에 표시한다.
- 오른쪽에 `주문하기`, `관리자` 메뉴를 표시한다.
- 현재 화면인 `주문하기`는 선택된 상태로 시각적으로 구분한다.
- `관리자` 메뉴를 선택하면 관리자 화면으로 이동한다.

### 4.2 메뉴 목록 영역

- 판매 가능한 메뉴를 카드 형태로 표시한다.
- 화면 너비에 따라 카드가 가로로 배치되며, 모바일에서는 세로 또는 다열 반응형으로 배치한다.
- 메뉴 카드에는 메뉴 이미지, 메뉴명, 기본 가격, 간단한 설명, 선택 가능한 옵션과 추가 금액, `담기` 버튼을 표시한다.

### 4.3 장바구니 영역

- 메뉴 목록 하단에 장바구니를 표시한다.
- 장바구니에는 담긴 메뉴명, 선택 옵션, 수량, 항목별 금액을 표시한다.
- 총 금액과 `주문하기` 버튼을 표시한다.
- 장바구니가 비어 있으면 빈 상태 안내 문구와 주문 불가 상태의 버튼을 표시한다.

## 5. 기능 요구사항

### FR-01. 메뉴 조회

- 주문하기 화면 진입 시 판매 중인 메뉴 목록을 조회한다.
- 각 메뉴는 이름, 이미지, 설명, 기본 가격, 옵션 정보를 포함한다.
- 판매 중지 또는 재고가 없는 메뉴는 주문할 수 없도록 표시한다.
- 메뉴 조회 중에는 로딩 상태를 표시한다.
- 메뉴 조회에 실패하면 오류 안내와 재시도 방법을 제공한다.

### FR-02. 메뉴 옵션 선택

- 사용자는 메뉴 카드에서 제공되는 옵션을 선택할 수 있다.
- 옵션은 체크박스 또는 해당 옵션에 적합한 입력 UI로 제공한다.
- 선택한 옵션의 추가 금액을 메뉴 가격에 반영한다.
- 현재 와이어프레임 기준 옵션 예시는 샷 추가(+500원), 시럽 추가(+0원)이다.
- 옵션 선택을 변경하면 메뉴의 주문 금액을 즉시 다시 계산한다.

### FR-03. 장바구니 담기

- `담기` 버튼을 누르면 선택한 옵션과 함께 메뉴를 장바구니에 추가한다.
- 기본 수량은 1개이다.
- 동일한 메뉴라도 선택 옵션 조합이 다르면 별도의 장바구니 항목으로 관리한다.
- 동일한 메뉴와 동일한 옵션 조합을 다시 담으면 별도 행을 추가하지 않고 수량을 증가시킨다.
- 담기 완료 후 장바구니와 총 금액을 즉시 갱신한다.

### FR-04. 장바구니 수량 및 항목 관리

- 각 장바구니 항목의 수량을 증가하거나 감소할 수 있어야 한다.
- 수량은 1개 미만이 될 수 없다.
- 수량 감소 결과가 0이 되는 경우 해당 항목을 삭제할지 확인하거나 즉시 삭제한다. 구현 시 한 가지 정책으로 일관되게 적용한다.
- 장바구니 항목을 개별 삭제할 수 있어야 한다.
- 수량 또는 항목이 변경되면 항목별 금액과 총 금액을 즉시 다시 계산한다.

### FR-05. 금액 계산

- 항목 금액은 `(기본 가격 + 옵션 추가 금액) × 수량`으로 계산한다.
- 총 금액은 모든 장바구니 항목 금액의 합계이다.
- 금액은 원화 단위로 표시하고 천 단위 구분을 적용한다.
- 화면에 표시되는 금액과 주문 요청에 저장되는 금액이 일치해야 한다.
- 주문 접수 시 서버가 최신 메뉴·옵션 가격으로 최종 검증하고 재계산한다.

### FR-06. 주문 접수

- 장바구니에 하나 이상의 항목이 있을 때만 `주문하기` 버튼을 활성화한다.
- `주문하기` 버튼을 누르면 주문 전 최종 확인을 제공한다.
- 최종 확인에는 메뉴명, 옵션, 수량, 항목별 금액, 총 금액을 표시한다.
- 사용자가 확인하면 주문 데이터를 서버에 전송한다.
- 주문 접수 중에는 중복 제출을 방지하기 위해 버튼을 비활성화하고 처리 상태를 표시한다.
- 주문 접수 성공 시 주문 완료 안내와 주문 식별 정보를 표시한다.
- 주문 접수 성공 후 장바구니를 비운다.
- 주문 접수 실패 시 입력한 장바구니를 유지하고 재시도할 수 있어야 한다.

### FR-07. 화면 이동

- `주문하기` 메뉴 선택 시 주문하기 화면으로 이동한다.
- `관리자` 메뉴 선택 시 관리자 화면으로 이동한다.
- 주문 접수 성공 후 주문 완료 화면 또는 완료 모달을 제공하고 다시 주문하기 화면으로 돌아갈 수 있어야 한다.

## 6. 데이터 요구사항

### 6.1 메뉴 데이터

- 메뉴 ID
- 메뉴명
- 이미지 URL
- 설명
- 기본 가격
- 판매 상태
- 재고 수량 또는 주문 가능 여부
- 옵션 목록

### 6.2 장바구니 항목 데이터

- 메뉴 ID
- 메뉴명
- 선택한 옵션 ID와 옵션명
- 옵션 추가 금액
- 수량
- 계산된 항목 금액

장바구니는 비회원 사용자를 위해 우선 프런트엔드 상태로 관리한다. 새로고침 후에도 유지할지는 구현 단계에서 `localStorage` 사용 여부를 결정한다.

### 6.3 주문 데이터

- 주문 ID
- 주문 항목 목록
- 메뉴별 옵션
- 메뉴별 수량
- 주문 총 금액
- 주문 상태
- 주문 생성 시각

## 7. 상태 및 예외 처리

### 7.1 필수 UI 상태

- 초기 로딩, 메뉴 조회 성공, 메뉴 없음, 메뉴 조회 실패
- 장바구니 비어 있음, 장바구니에 항목이 있는 상태
- 주문 접수 중, 주문 접수 성공, 주문 접수 실패

### 7.2 예외 상황

- 메뉴가 품절되거나 판매 중지된 경우 `담기` 버튼을 비활성화하고 상태를 표시한다.
- 주문 중 메뉴 가격이나 재고가 변경된 경우 서버 검증 결과를 안내하고 최신 정보로 갱신하도록 한다.
- 네트워크 오류가 발생한 경우 주문이 접수되지 않았음을 명확히 알리고 재시도할 수 있게 한다.
- 사용자가 주문 버튼을 연속 클릭한 경우 하나의 요청만 처리한다.
- 장바구니 항목이 주문 접수 전에 모두 삭제된 경우 주문을 막고 메뉴 선택을 안내한다.

## 8. 비기능 요구사항

- 데스크톱과 모바일 화면에서 기본적인 반응형 레이아웃을 지원한다.
- 버튼, 체크박스, 메뉴 링크는 키보드로 조작할 수 있어야 한다.
- 이미지가 로드되지 않아도 메뉴명, 가격, 설명을 확인할 수 있어야 한다.
- 금액 계산은 부동소수점 오차가 발생하지 않도록 정수 단위 원으로 처리한다.
- 주문 접수 API는 중복 요청에 대한 방어 로직을 가져야 한다.
- 사용자 인증과 결제 기능은 이번 범위에서 제외한다.

## 9. 수용 기준

- [ ] 주문하기 화면에 판매 중인 메뉴가 카드 목록으로 표시된다.
- [ ] 각 카드에서 메뉴명, 가격, 설명, 이미지, 옵션, 담기 버튼을 확인할 수 있다.
- [ ] 옵션을 선택하면 추가 금액이 정확히 반영된다.
- [ ] 메뉴를 담으면 선택한 옵션, 수량, 항목별 금액이 장바구니에 표시된다.
- [ ] 동일 메뉴·동일 옵션은 수량으로 합쳐지고, 옵션이 다르면 별도 항목으로 표시된다.
- [ ] 장바구니 수량 변경과 항목 삭제가 가능하다.
- [ ] 장바구니 변경 시 총 금액이 즉시 정확하게 갱신된다.
- [ ] 장바구니가 비어 있으면 주문하기 버튼을 사용할 수 없다.
- [ ] 주문 전 사용자가 최종 주문 내역과 총 금액을 확인할 수 있다.
- [ ] 주문 접수 중 중복 요청이 발생하지 않는다.
- [ ] 주문 성공 시 완료 안내가 표시되고 장바구니가 초기화된다.
- [ ] 주문 실패 시 장바구니가 유지되고 재시도할 수 있다.
- [ ] 메뉴 조회 및 주문 접수 실패 시 이해 가능한 오류 메시지가 표시된다.
- [ ] 데스크톱 및 모바일 화면에서 핵심 기능을 사용할 수 있다.

## 10. 범위 제외 및 후속 결정사항

- 사용자 회원가입 및 로그인
- 온라인 결제
- 쿠폰, 할인, 포인트
- 배달 주소 및 배달 상태 관리
- 주문 취소·환불 정책
- 장바구니의 로그인 사용자 간 동기화

위 항목은 기본 주문 흐름 구현 후 별도 요구사항으로 정의한다.

## 11. 관리자 화면 개요

### 11.1 관리자 목표

관리자는 관리자 화면에서 현재 주문 처리 현황과 메뉴별 재고를 한눈에 확인하고, 재고를 조정하며, 접수된 주문의 상태를 변경할 수 있어야 한다.

### 11.2 주요 사용자 작업

1. 전체 주문 및 주문 상태별 건수를 확인한다.
2. 메뉴별 현재 재고 수량을 확인한다.
3. 메뉴의 재고를 증가하거나 감소시킨다.
4. 접수된 주문의 상세 내역과 금액을 확인한다.
5. 주문을 `주문 접수`, `제조 중`, `제조 완료` 상태로 변경한다.

## 12. 관리자 화면 구성 및 레이아웃

와이어프레임 기준으로 화면은 상단 헤더, 관리자 대시보드, 재고 현황, 주문 현황 순서로 구성한다.

### 12.1 상단 헤더

- 브랜드명 `COZY`를 왼쪽에 표시한다.
- 오른쪽에 `주문하기`, `관리자` 메뉴를 표시한다.
- 현재 화면인 `관리자`는 선택된 상태로 시각적으로 구분한다.
- `주문하기` 메뉴를 선택하면 주문하기 화면으로 이동한다.

### 12.2 관리자 대시보드

- `관리자 대시보드` 제목을 표시한다.
- 다음 주문 집계 정보를 표시한다.
  - 총 주문
  - 주문 접수
  - 제조 중
  - 제조 완료
- 대시보드 수치는 관리자 화면 진입 시 조회하고, 주문 상태 변경 후 즉시 갱신한다.
- 각 수치는 동일한 기준 시점의 데이터로 구성되어야 한다.

### 12.3 재고 현황

- `재고 현황` 영역에 판매 메뉴를 카드 형태로 표시한다.
- 각 카드에는 메뉴명과 현재 재고 수량을 표시한다.
- 메뉴별로 `+`와 `-` 버튼을 제공해 재고를 1개 단위로 조정한다.
- 재고는 0개 미만으로 내려갈 수 없다.
- 재고가 0개인 메뉴는 주문하기 화면에서 품절 또는 주문 불가 상태로 표시한다.
- 재고 변경이 완료되면 해당 카드의 수량을 즉시 갱신한다.

### 12.4 주문 현황

- `주문 현황` 영역에 주문 목록을 표시한다.
- 각 주문 항목에는 주문 시각, 메뉴명, 옵션, 수량, 금액, 현재 상태를 표시한다.
- 와이어프레임 기준으로 주문 항목 오른쪽에 `주문 접수` 버튼을 제공한다.
- 버튼 또는 상태 컨트롤은 현재 상태에 따라 다음 상태로 변경할 수 있도록 한다.
- 주문이 여러 건인 경우 최신 주문이 위에 표시되도록 정렬한다.
- 주문이 없으면 빈 상태 안내 문구를 표시한다.

## 13. 관리자 기능 요구사항

### AR-01. 관리자 데이터 조회

- 관리자 화면 진입 시 대시보드 집계, 메뉴 재고, 주문 목록을 조회한다.
- 세 영역은 로딩 상태를 지원해야 한다.
- 조회 중에는 조작 가능한 버튼을 비활성화하거나 처리 중 상태를 표시한다.
- 조회에 실패한 영역에는 오류 메시지와 재시도 기능을 제공한다.

### AR-02. 주문 집계

- 총 주문 수는 조회 기준에 포함된 전체 주문 수이다.
- 주문 접수, 제조 중, 제조 완료 수는 각 상태에 해당하는 주문 수이다.
- 하나의 주문은 현재 상태에 따라 하나의 상태 집계에만 포함된다.
- 주문 상태가 변경되면 기존 상태의 수는 감소하고 새 상태의 수는 증가해야 한다.
- 조회 기준 기간을 별도로 정의하지 않은 초기 버전에서는 전체 주문을 대상으로 한다.

### AR-03. 재고 증가

- 재고 카드의 `+` 버튼을 누르면 해당 메뉴 재고가 1개 증가한다.
- 변경 요청이 성공하면 화면의 수량을 최신 서버 값으로 갱신한다.
- 처리 중에는 연속 클릭으로 중복 요청이 발생하지 않아야 한다.
- 재고 증가 실패 시 기존 수량을 유지하고 오류 메시지를 표시한다.

### AR-04. 재고 감소

- 재고 카드의 `-` 버튼을 누르면 해당 메뉴 재고가 1개 감소한다.
- 재고가 0개일 때 `-` 버튼은 비활성화한다.
- 변경 요청이 성공하면 화면의 수량을 최신 서버 값으로 갱신한다.
- 재고 감소 실패 시 기존 수량을 유지하고 오류 메시지를 표시한다.

### AR-05. 재고와 주문 가능 상태 연동

- 재고가 0개가 되면 해당 메뉴를 주문하기 화면에서 주문할 수 없어야 한다.
- 재고가 다시 1개 이상이 되면 해당 메뉴는 주문 가능한 상태로 전환된다.
- 실제 재고 차감 시점은 주문 생성 시점 또는 주문 접수 시점 중 하나로 정하고, 백엔드와 프런트엔드에서 동일하게 적용한다.
- 주문 처리 중 재고가 부족해지는 경우 서버가 주문을 거부하고 관리자와 사용자에게 결과를 전달한다.

### AR-06. 주문 상태 변경

- 주문은 다음 상태를 가진다.
  - 주문 접수
  - 제조 중
  - 제조 완료
- 초기 주문 상태는 `주문 접수`이다.
- `주문 접수` 상태의 주문은 `제조 중`으로 변경할 수 있다.
- `제조 중` 상태의 주문은 `제조 완료`로 변경할 수 있다.
- 완료된 주문은 기본 흐름에서 이전 상태로 되돌릴 수 없다.
- 상태 변경 성공 시 버튼, 주문 상태, 대시보드 집계를 즉시 갱신한다.
- 상태 변경 중에는 해당 주문의 상태 버튼을 비활성화한다.
- 상태 변경 실패 시 기존 상태를 유지하고 재시도할 수 있어야 한다.

### AR-07. 주문 상세 확인

- 관리자는 주문 항목에서 메뉴명, 옵션, 수량, 금액을 확인할 수 있어야 한다.
- 주문에 여러 메뉴가 포함된 경우 하나의 주문 단위로 묶어서 표시한다.
- 주문 총 금액은 주문하기 화면에서 생성된 금액과 일치해야 한다.
- 주문 시각은 관리자 화면에서 식별하기 쉬운 날짜·시간 형식으로 표시한다.

- 주문 처리 중 메뉴 재고가 부족해진 경우 주문 상태를 임의로 변경하지 않고 오류 원인을 표시한다.
- 네트워크 오류가 발생하면 변경 전 상태를 임의로 확정하지 않고 재시도할 수 있게 한다.

- 서버는 재고 변경과 주문 상태 변경을 원자적으로 처리해야 한다.
- 관리자 인증 및 권한 관리는 이번 초기 범위에서는 제외하되, 실제 운영 전 필수 도입 항목으로 남긴다.

## 17. 관리자 수용 기준

- [ ] 관리자 화면에 `관리자 대시보드`, `재고 현황`, `주문 현황` 영역이 표시된다.
- [ ] 헤더에서 현재 화면이 `관리자`임을 확인할 수 있다.
- [ ] 대시보드에 총 주문, 주문 접수, 제조 중, 제조 완료 건수가 표시된다.
- [ ] 메뉴별 재고 수량이 카드 형태로 표시된다.
- [ ] `+` 버튼으로 재고가 1개 증가한다.
- [ ] `-` 버튼으로 재고가 1개 감소하며, 재고가 0개일 때는 더 감소하지 않는다.
- [ ] 재고가 0개인 메뉴는 주문하기 화면에서 주문할 수 없다.
- [ ] 주문 현황에 주문 시각, 메뉴, 옵션, 수량, 금액, 상태가 표시된다.
- [ ] 주문 접수 상태의 주문을 제조 중으로 변경할 수 있다.
- [ ] 제조 중 상태의 주문을 제조 완료로 변경할 수 있다.
- [ ] 주문 상태 변경 후 주문 목록과 대시보드 집계가 함께 갱신된다.
- [ ] 재고 또는 주문 상태 변경 중 중복 요청이 발생하지 않는다.
- [ ] 조회 및 변경 실패 시 오류 메시지와 재시도 방법이 제공된다.
- [ ] 주문이나 메뉴가 없을 때 빈 상태가 명확하게 표시된다.

## 19. 백엔드 개발 개요

### 19.1 목적

백엔드는 메뉴, 옵션, 재고, 주문 데이터를 영속적으로 저장하고 주문하기 화면과 관리자 화면에 필요한 데이터를 제공한다. 프런트엔드의 표시 상태나 금액을 그대로 신뢰하지 않고, 서버가 메뉴 가격·옵션 가격·재고·주문 상태를 최종 검증한다.

### 19.2 백엔드 범위

- 메뉴와 옵션 데이터의 등록·조회·수정·삭제
- 주문 생성 및 주문 상세 조회
- 주문 목록과 관리자용 주문 상태 조회
- 주문 상태 변경
- 재고 조회 및 재고 증감
- 주문 생성과 재고 변경의 트랜잭션 처리
- 잘못된 요청과 재고 부족에 대한 일관된 오류 응답

## 20. 데이터 모델

### 20.1 Menus

커피 메뉴의 기본 정보와 현재 재고를 저장한다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | BIGSERIAL | O | 메뉴 식별자 |
| name | VARCHAR(100) | O | 커피 이름 |
| description | TEXT | X | 메뉴 설명 |
| price | INTEGER | O | 기본 가격. 원 단위의 0 이상 정수 |
| image_url | TEXT | X | 메뉴 이미지 주소 |
| stock_quantity | INTEGER | O | 현재 재고 수량. 0 이상 정수 |
| is_available | BOOLEAN | O | 판매 가능 여부 |
| created_at | TIMESTAMPTZ | O | 생성 시각 |
| updated_at | TIMESTAMPTZ | O | 최종 수정 시각 |

재고가 0이면 주문 불가로 처리한다. `is_available`가 false인 메뉴도 주문할 수 없다.

### 20.2 Options

메뉴에 연결되는 추가 옵션과 추가 가격을 저장한다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | BIGSERIAL | O | 옵션 식별자 |
| menu_id | BIGINT | O | 연결할 Menus의 id |
| name | VARCHAR(100) | O | 옵션 이름 |
| price | INTEGER | O | 옵션 가격. 원 단위의 0 이상 정수 |
| is_available | BOOLEAN | O | 옵션 선택 가능 여부 |
| created_at | TIMESTAMPTZ | O | 생성 시각 |
| updated_at | TIMESTAMPTZ | O | 최종 수정 시각 |

`Options.menu_id`는 `Menus.id`를 참조하는 외래 키이다. 메뉴가 삭제될 때 연결된 옵션의 처리 정책은 기본적으로 함께 삭제하거나 삭제를 제한하는 방식 중 하나로 정하고 일관되게 적용한다.

### 20.3 Orders

주문 단위의 시각, 총 금액, 처리 상태를 저장한다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | BIGSERIAL | O | 주문 식별자 |
| ordered_at | TIMESTAMPTZ | O | 주문 일시 |
| total_amount | INTEGER | O | 주문 총 금액. 원 단위 |
| status | VARCHAR(20) | O | `received`, `making`, `complete` |
| created_at | TIMESTAMPTZ | O | 레코드 생성 시각 |
| updated_at | TIMESTAMPTZ | O | 최종 수정 시각 |

### 20.4 OrderItems

사용자가 요청한 주문 내용(메뉴, 수량, 옵션, 금액)을 주문과 분리해 저장한다. `Orders`에 JSON 문자열만 저장하지 않고 주문 항목을 별도 테이블로 관리해 관리자 화면과 주문 상세 API에서 안정적으로 조회할 수 있도록 한다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | BIGSERIAL | O | 주문 항목 식별자 |
| order_id | BIGINT | O | 연결할 Orders의 id |
| menu_id | BIGINT | O | 주문 당시 메뉴 식별자 |
| menu_name | VARCHAR(100) | O | 주문 당시 메뉴명 스냅샷 |
| quantity | INTEGER | O | 주문 수량. 1 이상 정수 |
| unit_price | INTEGER | O | 옵션을 포함한 주문 당시 단가 |
| line_amount | INTEGER | O | `unit_price × quantity` |

### 20.5 OrderItemOptions

주문 시 선택한 옵션을 보존한다. 메뉴나 옵션 가격이 이후 변경되어도 과거 주문 금액이 바뀌지 않도록 옵션명과 가격을 스냅샷으로 저장한다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | BIGSERIAL | O | 주문 옵션 식별자 |
| order_item_id | BIGINT | O | 연결할 OrderItems의 id |
| option_id | BIGINT | X | 원본 Options의 id |
| option_name | VARCHAR(100) | O | 주문 당시 옵션명 |
| option_price | INTEGER | O | 주문 당시 옵션 추가 금액 |

### 20.6 관계

- Menus 1 : N Options
- Menus 1 : N OrderItems
- Orders 1 : N OrderItems
- OrderItems 1 : N OrderItemOptions
- Options 1 : N OrderItemOptions

### 20.7 데이터 제약조건

- 가격과 재고 수량은 음수가 될 수 없다.
- 주문 수량은 1 이상이어야 한다.
- 주문 총액은 서버가 주문 항목 금액을 합산해 계산한다.
- 주문 상태는 `received`, `making`, `complete` 중 하나만 허용한다.
- 주문 상태는 `received → making → complete` 순서로만 변경할 수 있다.
- 삭제된 메뉴와 옵션도 과거 주문의 이름·가격·옵션 정보를 확인할 수 있도록 주문 스냅샷을 보존한다.

## 21. 데이터 스키마 사용자 흐름

### 21.1 메뉴 조회 및 화면 표시

1. 사용자가 `주문하기` 메뉴를 클릭한다.
2. 프런트엔드가 `GET /api/menus`를 호출한다.
3. 서버가 판매 가능한 메뉴와 연결된 옵션 목록을 반환한다.
4. 프런트엔드는 메뉴명, 설명, 가격, 이미지를 메뉴 카드에 표시한다.
5. 재고 수량은 관리자 화면에서 표시하고, 주문 화면에서는 재고가 없는 메뉴를 품절·주문 불가로 표시한다.

### 21.2 메뉴 선택 및 장바구니

1. 사용자가 메뉴 카드에서 옵션을 선택한다.
2. 프런트엔드는 메뉴 ID, 옵션 ID, 수량을 장바구니에 저장한다.
3. 장바구니에는 메뉴명, 옵션, 수량, 예상 금액을 표시한다.
4. 동일 메뉴와 동일 옵션 조합은 수량으로 합산하고, 옵션 조합이 다르면 별도 항목으로 표시한다.

### 21.3 주문 생성

1. 사용자가 장바구니에서 `주문하기` 버튼을 클릭한다.
2. 프런트엔드는 메뉴 ID, 옵션 ID, 수량만 서버에 전달한다.
3. 서버는 트랜잭션 안에서 메뉴 판매 여부, 옵션 연결 여부, 최신 가격, 재고를 다시 검증한다.
4. 서버는 최신 데이터로 주문 항목 금액과 총 금액을 계산한다.
5. 서버는 Orders, OrderItems, OrderItemOptions를 저장한다.
6. 서버는 주문 생성과 동시에 주문 수량만큼 Menus의 재고를 차감한다.
7. 모든 저장과 재고 차감이 성공하면 주문 상태 `received`와 주문 ID를 반환한다.
8. 하나라도 실패하면 전체 트랜잭션을 롤백하고 주문을 저장하지 않는다.

초기 백엔드 정책에서는 주문 생성 시 재고를 차감하며, `제조 완료` 상태 변경 시 재고를 다시 차감하지 않는다. 이를 통해 주문 접수와 제조 완료 사이의 중복 차감을 방지한다.

### 21.4 관리자 주문 처리

1. 관리자가 관리자 화면을 연다.
2. 프런트엔드는 주문 집계, 재고, 주문 목록을 조회한다.
3. 서버는 새로 생성된 주문을 기본 상태 `received`로 반환한다.
4. 관리자가 `주문 접수` 또는 `제조 시작` 동작을 수행하면 상태를 `making`으로 변경한다.
5. 관리자가 제조 완료 동작을 수행하면 상태를 `complete`로 변경한다.
6. 상태 변경 후 관리자 화면은 주문 목록과 대시보드 집계를 다시 반영한다.

## 22. API 설계

### 22.1 공통 규칙

- 기본 경로: `/api`
- 요청·응답 형식: `application/json`
- 금액은 원 단위 정수로 주고받는다.
- 날짜·시간은 ISO 8601 형식의 UTC 또는 서버가 정한 단일 시간대 형식으로 통일한다.
- 성공 응답은 `data` 필드를 사용하고, 오류 응답은 `error.code`, `error.message`를 포함한다.

### 22.2 메뉴 목록 조회

`GET /api/menus`

주문하기 화면에 표시할 메뉴와 옵션 목록을 반환한다.

응답 예시:

```json
{
  "data": [
    {
      "id": 1,
      "name": "아메리카노(ICE)",
      "description": "깔끔하고 시원한 산미의 아이스 아메리카노",
      "price": 4000,
      "imageUrl": "/images/americano-ice.png",
      "isAvailable": true,
      "options": [
        { "id": 1, "name": "샷 추가", "price": 500 },
        { "id": 2, "name": "시럽 추가", "price": 0 }
      ]
    }
  ]
}
```

### 22.3 관리자용 재고 조회

`GET /api/admin/inventory`

메뉴명, 재고 수량, 판매 가능 여부, 재고 상태를 반환한다. 재고 상태는 서버 또는 프런트엔드에서 다음 기준으로 계산한다.

- `0`: 품절
- `1~4`: 주의
- `5 이상`: 정상

### 22.4 주문 생성

`POST /api/orders`

요청 예시:

```json
{
  "items": [
    {
      "menuId": 1,
      "quantity": 1,
      "optionIds": [1]
    }
  ]
}
```

응답에는 서버가 생성한 주문 ID, 주문 일시, 주문 상태, 서버 계산 총 금액과 주문 항목을 포함한다.

### 22.5 주문 단건 조회

`GET /api/orders/:orderId`

주문 ID를 전달하면 주문 일시, 상태, 메뉴명, 수량, 옵션, 단가, 항목 금액, 총 금액을 반환한다.

### 22.6 관리자 주문 목록 조회

`GET /api/admin/orders?status=received`

관리자 화면의 주문 현황에 표시할 주문 목록과 주문 상태별 집계를 반환한다. `status`는 선택적 필터이며, 미입력 시 전체 주문을 최신 주문순으로 반환한다.

### 22.7 주문 상태 변경

`PATCH /api/admin/orders/:orderId/status`

요청 예시:

```json
{
  "status": "making"
}
```

서버는 현재 상태와 요청 상태가 허용된 전이인지 확인한 후 변경한다. 허용되지 않은 전이는 `409 CONFLICT`로 응답한다.

### 22.8 재고 변경

`PATCH /api/admin/menus/:menuId/stock`

요청 예시:

```json
{
  "delta": 1
}
```

`delta`는 재고 증감량이며, 결과 재고가 0 미만이 되면 변경하지 않고 오류를 반환한다. 재고 변경은 데이터베이스에서 원자적으로 처리한다.

## 23. 오류 응답 및 동시성 처리

### 23.1 표준 오류 코드

- `400 BAD_REQUEST`: 필수 필드 누락, 잘못된 수량 또는 형식
- `404 NOT_FOUND`: 메뉴, 옵션, 주문을 찾을 수 없음
- `409 CONFLICT`: 재고 부족, 잘못된 주문 상태 전이, 동시 수정 충돌
- `500 INTERNAL_SERVER_ERROR`: 서버 내부 오류

### 23.2 재고 동시성

- 주문 생성 시 재고 확인과 차감을 하나의 트랜잭션으로 처리한다.
- 재고 차감 SQL은 현재 재고가 주문 수량 이상일 때만 성공하도록 조건을 둔다.
- 동시 주문으로 재고가 부족해진 요청은 `409 STOCK_INSUFFICIENT`를 반환한다.
- 관리자 재고 변경도 원자적 업데이트를 사용해 음수 재고를 방지한다.

### 23.3 중복 주문 방지

- 주문 생성 API는 클라이언트가 전달하는 요청 식별자(`Idempotency-Key`)를 선택적으로 지원한다.
- 동일한 키로 재요청하면 새 주문을 만들지 않고 기존 주문 결과를 반환한다.
- 프런트엔드는 주문 요청 중 버튼을 비활성화한다.

## 24. 백엔드 수용 기준

- [ ] `GET /api/menus`가 메뉴와 연결된 옵션을 반환한다.
- [ ] 주문 화면에 메뉴명, 설명, 가격, 이미지가 표시된다.
- [ ] 재고가 0인 메뉴는 주문 화면에서 주문할 수 없다.
- [ ] 관리자는 메뉴별 재고 수량과 정상·주의·품절 상태를 확인할 수 있다.
- [ ] 관리자는 메뉴 재고를 1개 단위로 증감할 수 있다.
- [ ] 장바구니의 메뉴 ID, 옵션 ID, 수량으로 주문을 생성할 수 있다.
- [ ] 주문 생성 시 서버가 최신 가격으로 금액을 재계산한다.
- [ ] 주문 생성 시 Orders와 주문 항목 데이터가 함께 저장된다.
- [ ] 주문 생성과 재고 차감이 하나의 트랜잭션으로 처리된다.
- [ ] 주문 생성 후 주문 상태가 `received`로 저장된다.
- [ ] 주문 ID로 주문 상세를 조회할 수 있다.
- [ ] 관리자 주문 목록에서 주문 일시, 메뉴, 수량, 옵션, 금액, 상태를 확인할 수 있다.
- [ ] 주문 상태가 `received → making → complete` 순서로 변경된다.
- [ ] 제조 완료 상태 변경으로 재고가 중복 차감되지 않는다.
- [ ] 재고 부족, 존재하지 않는 메뉴, 잘못된 상태 전이에 대해 명확한 오류 응답을 반환한다.
- [ ] 동시 주문에서도 재고가 음수가 되거나 초과 판매되지 않는다.
